# 실행 기록에서 워크플로로 — 판단은 필요한 곳에만

NLC의 목표는 세 가지를 잇는 것입니다.

1. **에이전트가 처음 하는 일을 직접 조작한다** — 레시피가 없는 작업은 모델이 화면을 보며 합니다.
2. **그 실행을 매개변수가 있는 워크플로로 만든다** — 다음부터는 모델 없이 재실행합니다.
3. **판단이 필요한 곳에서만 에이전트가 개입한다** — 미리 정해 둔 판단 지점과, 예상 못 한 상황에서만.

이 문서는 그 흐름 전체와, 각 단계가 무엇을 확인하는지 설명합니다. Python API는
[`api.md`](api.md), 에이전트용 작성 가이드는 [`../skill/SKILL.md`](../skill/SKILL.md)에 있습니다.

## 한눈에 보기

```
nlc do "계산기에서 25의 제곱근 구해줘"      ① 레시피가 없으면 에이전트가 화면을 보며 조작
        │  검증된 실행이면 후보로 저장 (flows/_candidates/)
        ▼
nlc candidates                              ② 후보와, 아직 레시피가 될 수 없는 이유
nlc promote <후보> -p 25=n                  ③ 승격: 입력 지정 · 판단 지점 검토 · 검사 통과 시 저장
        ▼
nlc do "계산기로 49 제곱근 좀 알려줘요"     ④ 저장된 레시피를 찾아 모델 없이 재실행 (결과 7)
        │  판단 단계에서만 모델에 한 번 묻고, 처음 보는 경우는 그 지점부터 에이전트가 이어서 조작
        ▼
     레시피가 경우별로 자란다 (branches)
```

아래 숫자는 모두 실제 계산기와 실제 모델로 잰 것입니다(2026-09-23 ~ 09-25).

## ① 에이전트가 직접 조작하기 — walk

레시피가 없는 요청은 `nlc do`가 화면 단위 루프(`nlc/general.py`)로 처리합니다. 모델에게는
**클릭마다가 아니라 화면마다** 한 번 묻습니다. 실행 기록에는 각 단계마다 다음이 남습니다.

| 기록 | 쓰임 |
|---|---|
| `screen_options` | 같은 화면에 있던 같은 종류의 다른 선택지 — 판단 단계의 선택지 후보 |
| `screen_reads` | 그때 화면에 보이던 값 — 판단의 근거, 복사·추출할 값의 출처 |
| `screen_change` | 그 단계 뒤 화면에서 나타나거나 사라진 요소 — 살펴보기만 한 단계 판별 |
| `effect` (메뉴) | 메뉴 실행 뒤 바뀐 요소 — 메뉴 단계의 결과 조건 |

실행이 **결과까지 검증된 경우에만** 후보가 저장됩니다. 요청 읽기가 "계산해서 알려줘"를
"값 읽기"로 잘못 분류하면 검증이 되지 않고 후보도 남지 않습니다 — 틀린 레시피보다 낫습니다.

## ② 후보 — 레시피가 되기 전 단계

```bash
nlc candidates
  [준비됨] 계산기로_의_제곱근_ce4ab9  (1회)  계산기로 25의 제곱근 구하기
           부탁에서 온 값: 25
           살펴보기만 한 단계(레시피에서 뺌): Mode
```

- **부탁에서 온 값** — 요청 문장에서 온 값만 입력 후보입니다. 화면에서 읽은 값은 이번
  실행의 데이터라 템플릿에 들어가면 안 됩니다. 한 자리씩 누른 숫자는 하나의 값(`25`)으로 묶입니다.
- **살펴보기만 한 단계** — 팝업을 열어 보기만 하고 쓰지 않은 클릭은 뺍니다. 네 조건을 모두 만족할 때만:
  새 요소가 나타나기만 했고 기존 요소는 안 바뀌었다 · 뒤 단계가 그 요소를 쓰지 않았다 ·
  다음 단계 뒤 사라졌다 · 뒤에 실제로 동작하는 단계가 남아 있다.
- **[아직]** 이면 이유가 같이 나옵니다(예: 메뉴 단계에 결과 조건이 없음).

## ③ 승격 — `nlc promote <후보> [-p 값=이름] [--no-decisions]`

승격은 모델이 제안하고, **실행 기록이 결정**합니다.

### 입력 지정 (`-p`)

`-p 25=n` 은 요청에서 온 값 `25`를 입력 `n`으로 바꿉니다.

- 요청에서 오지 않은 값은 거부합니다.
- 만든 템플릿에 원래 값을 넣었을 때 **원래 실행과 똑같아야** 저장합니다.
- 레시피는 자신이 답하는 문장(`intents`)을 함께 저장합니다 — `계산기에서 {{n}}의 제곱근 구해줘`.

### 화면에서 읽은 값을 입력한 단계 (자동)

| 에이전트가 입력한 것 | 레시피에서 |
|---|---|
| 보이던 값 **전체** | 재실행 때 그 값을 새로 읽어 그대로 입력 (모델 없음) |
| 보이던 글의 **일부** | 읽기 → `extract` 판단 → 입력 |
| 요청에도 화면에도 **없던 글** (에이전트가 쓴 글) | `compose` 판단 → 입력 |

승격 검사는 "이번 실행에서 읽은 값을 담은 단계"를 거부합니다. 위처럼 바뀐 단계에서
봐주는 것은 **그 단계에 실제로 들어갔던 값뿐**이고, 다른 값을 끼워 넣으면 여전히 걸립니다.

### 판단 지점 검토 (모델 1회)

화면에 보이던 값이 있는 상태에서 누른 단계가 있으면, 모델이 실행 기록을 한 번 검토해
"화면을 보고 고른 단계"를 제안합니다. 제안은 두 종류입니다.

- **`this_step`** — 이 단계에서 누르는 것 하나만 달라짐 (예: 짝수면 `2`, 홀수면 `3`).
- **`rest`** — 이 단계부터 뒤가 통째로 달라짐 (예: 짝수면 ×2, 홀수면 +1). 분기가 됩니다.
  뒤에서 또 경우가 나뉘면 안쪽 분기가 됩니다.

제안이 받아들여지려면 **모두** 만족해야 합니다.

- 판단의 근거(`depends_on`)가 그 단계에서 실제로 보이던 값이다.
- `this_step`: 선택지가 그 화면에 있던 것이고, 실제로 누른 것을 포함한다.
- 요청이 이미 정한 값이 아니다 — 단, 요청이 선택지를 둘 이상 말했다면("짝수면 2, 홀수면 3") 판단이다.
- 저장·전송처럼 되돌릴 수 없는 결과를 남기는 단계가 아니다.
- `rest`: 재실행 때 쓸 판단 모델에게 **기록 당시 화면 값을 보여주고 다시 물어서** 같은 답이 나온다.
  다르면 그 분기는 다른 경우에 재생될 것이므로 받지 않는다.
- 판단을 넣은 레시피에 실행 당시의 답을 따라가면 **원래 실행과 똑같다**.

## ④ 재실행 — 찾기, 실행, 판단

### 레시피 찾기 (싼 순서대로)

| 단계 | 비용 | 예 |
|---|---|---|
| 저장된 문장 그대로 | 모델 0 | `계산기에서 49의 제곱근 구해줘` |
| 핵심 단어가 같음 | 모델 0 | `계산기로 49 제곱근 좀 알려줘요` |
| 요청 읽기 | 모델 1 | `계산기로 16의 루트값 좀 알려줄래` |

- 핵심 단어 매칭은 조사·어미·군말을 떼고 **핵심 단어와 동사가 정확히 같을 때만** 맞춥니다.
  "구해/계산해/알려"처럼 "알아내 줘" 뜻의 동사만 뺍니다 — `곱해줘`와 `나눠줘`는 다른 요청입니다.
  입력은 숫자만, 숫자가 둘 이상이면 순서가 아니라 조사로 구분합니다(`9를 3으로` = `3으로 9를`).
  부정·제외 표현(`말고`, `빼고`…)이 있으면 모델로 보냅니다. `5를 빼고`처럼 숫자 뒤의 `빼고`는 빼기입니다.
- 요청 읽기는 한 번의 호출로 뜻과 레시피와 값을 함께 고릅니다. 레시피는 목록 안에서만,
  값은 **사용자가 한 말에 글자 그대로 있어야** 합니다.
- 요청 읽기로 찾은 요청이 성공하면 그 말투를 레시피에 추가합니다. 다음부터는 모델 0입니다.

### 판단 단계 (`decide`)

판단 단계는 화면에 아무것도 하지 않습니다. 모델에게 한 번 묻고, 답을 뒤 단계가 `{{이름}}`으로 씁니다.

```jsonc
// 고르기 — 답은 선택지 중 하나
{ "action": "decide",
  "params": { "question": "계산기 화면의 수가 짝수입니까?", "choices": ["2", "3"], "into": "k" } }

// 뽑기 — 답은 읽은 값 안에 글자 그대로 있어야 함
{ "action": "decide",
  "params": { "question": "주문번호만 고르십시오", "extract_from": ["source"], "into": "order" } }

// 쓰기 — 자유로운 글, 입력값으로만 쓸 수 있음
{ "action": "decide",
  "params": { "question": "문의에 대한 두 문장짜리 답장", "compose": true, "into": "reply" } }

// 분기 — 답에 따라 뒤가 통째로 달라짐 (분기 안에 또 판단 가능)
{ "action": "decide",
  "params": { "question": "짝수입니까, 홀수입니까?", "choices": ["짝수", "홀수"], "into": "case",
              "goal": "짝수면 2를 곱하고 홀수면 1을 더하기",
              "branches": { "홀수": [ /* 이 경우의 단계들 */ ] } } }
```

규칙:

- `into` 는 영문 이름이고, 레시피 전체(분기 안 포함)에서 겹치면 안 됩니다.
- 판단 모델이 없으면 추측하지 않고 `decision_unavailable` 로 멈춥니다.
- 민감한 값으로 표시된 capture(`"sensitive": true`)는 모델에게 보여주지 않습니다.
- 판단으로 정한 값이 **승인이 필요한 단계**로 들어가면, 값이 정해진 그 시점에 **실제 값을 보여주고** 묻습니다
  (`compose`는 전문). 실행 전에는 묻지 않습니다 — 아무도 그 값을 모르니까요. 물을 방법이 없으면 실행 전에 거부합니다.
- `compose`로 쓴 글은 입력할 내용으로만 쓸 수 있습니다. 무엇을 누를지 정하는 데 쓰면 거부합니다.

### 분기가 자라는 방식

분기 판단이 **단계가 없는 답**을 고르면, 그 지점부터 에이전트가 화면을 보며 이어서 합니다.

- 그 실행이 검증되고 승격 검사를 통과하면 그 답의 분기로 **그 깊이에** 저장합니다.
- 새 분기도 판단 지점 검토를 거칩니다 — 새 분기 안의 판단도 찾습니다.
- 그 실행에서 쓴 입력값은 다시 `{{입력}}`으로 바꾸고, 원래 값으로 재현되는지 확인합니다.
- 승인이 필요한 단계가 들어간 분기는 그 실행에서만 쓰고 저장하지 않습니다.

실측 — "화면의 수가 짝수면 ×2, 홀수면 +1, 그다음 20보다 크면 −5, 아니면 +5":

```
화면 수 읽기 → 짝수/홀수?
  [홀수] +1 → 읽기 → 20 초과?
           [20 이하] +5 =        ← 7 로 처음 실행 (13)
           [20보다 큼] −5 =      ← 25 일 때 배움 (21)
  [짝수] ×2 = → 읽기 → Subtract/Add 고르기 → 5 =   ← 12 일 때 배움 (19)
```

이후 4 → 13, 27 → 23 은 판단 호출만으로 재실행됐습니다.

### 예상 못 한 상황 — 다시 지목 (`--think`)

에이전트 실행에서 만든 레시피는 그때 화면이 보여준 이름을 기록합니다. 계산기의 `Clear`는
표시창이 비면 `All Clear`가 됩니다. 이런 경우:

- 되돌릴 수 없는 결과를 남기지 않는 단계는 `target_missing`/`target_ambiguous` 에서 모델에게 한 번 물어 대상을 다시 고릅니다.
- 에이전트 실행에서 승격된 레시피는 기본 1회, 직접 작성한 레시피는 기본 0회입니다. `--think N`으로 정하고 `--think 0`으로 끕니다.
  `nlc do`, `nlc run`, `nlc replay` 모두 같습니다.
- 다시 고른 대상은 이번 실행에만 쓰고 레시피에 저장하지 않습니다.

## 오류 코드

| 오류 | 뜻 |
|---|---|
| `decision_unavailable` | 판단 단계인데 답할 모델이 없음 (쓰기 판단은 쓰기를 지원하는 판단 모델만) |
| `decision_invalid` | 선택지 밖의 답 · 읽은 글에 없는 추출 · 빈 글 |
| `decision_failed` | 판단 모델 호출이 실패함 |
| `decision_drives_consent` | 판단 값이 승인 필요 단계로 가는데 물을 방법(`confirm`)이 없음 |
| `composed_text_aims` | 모델이 쓴 글이 입력값이 아닌 곳(선택자 등)에 쓰임 |
| `branch_unwalked` | 단계가 없는 분기인데 이어서 조작할 에이전트가 없음 |
| `branch_walk_failed` | 이어서 조작했지만 끝까지 가지 못함 |
| `gated` / `declined` | 실행 중 승인 질문에 아니오 |

나머지 재실행 오류는 [`../skill/SKILL.md`](../skill/SKILL.md#when-a-run-fails)를 보세요.

## 한계

- 판단의 근거가 화면에 나타난 적이 없는 중간값일 수 있습니다. 에이전트가 여러 단계를 한 번에
  눌러 7+1=8 을 화면에 띄우지 않았다면, 재실행 때 그 시점의 표시창에는 8이 아닙니다. 판단 모델이
  앞서 읽은 값으로 계산해 맞힌 사례는 있지만, 보이는 값을 근거로 하는 판단보다 덜 확실합니다.
- 핵심 단어 매칭은 숫자 입력만 다룹니다. 이름·문장 입력은 요청 읽기로 찾습니다.
- 분기를 배우는 실행에 저장·전송이 들어가면 그 분기는 저장되지 않습니다.
